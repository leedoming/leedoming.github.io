선택 기준

“EC2보다 좋아서”가 아니라 당시 조건 때문에 선택했습니다. EC2로도 확장 구조는 만들 수 있습니다. 판단 기준은 아래 네 가지였습니다.

  • 다중 모델 파이프라인을 이미지 크기 제약 없이 실행할 것
  • 컨테이너 단위로 내부에서 수정·관리할 수 있을 것
  • 서버 프로비저닝·OS 관리 없이 운영을 단순화할 것
  • API 기반 서비스로 요청 증가에 대응할 구조일 것
Takeaway

관리형 서비스는 편의성과 함께 서비스 한도가 따라옵니다. 이후에는 서비스를 고르기 전에 워크로드 특성(모델 수, 이미지 크기, 실행 시간)과 공식 문서의 제약을 먼저 대조합니다.

resource "azurerm_container_group" "chromadb" {
  ip_address_type = "Private"
  subnet_ids      = [azurerm_subnet.container_instances.id]
  container {
    ports  { port = 8000 }
    volume {
      mount_path = "/data"
      share_name = azurerm_storage_share.chromadb.name
    }
  }
}

# main-app / search-app
env {
  name  = "CHROMADB_HOST"
  value = azurerm_container_group.chromadb.ip_address
}

설계 판단

서비스별 위임 서브넷

ACI와 Container Apps는 각자 서브넷 위임이 필요해 한 서브넷에 둘 수 없습니다. 서브넷을 서비스 단위로 나눠 공개 앱 영역과 내부 DB 영역의 경계로 삼았습니다.

DB는 사설 IP로만 노출

ChromaDB에는 공개 IP를 주지 않고, 앱은 VNet 안에서 사설 IP로 접근합니다. 외부 ingress는 두 웹 앱에만 열었습니다.

VM 대신 ACI — 그리고 데이터 영속성

초기 설계는 ChromaDB를 VM + Docker로 두었지만, Azure를 처음 다루며 컨테이너 서비스인 ACI를 직접 써 보려고 ACI로 구현했습니다. ACI는 컨테이너를 다시 만들면 데이터가 사라지므로, Azure Files를 /data에 마운트해 벡터 데이터를 영구 저장했습니다.

기존 리소스는 참조만

미리 만들어진 Resource Group과 ACR은 data 소스로 읽기만 해서, 이 코드를 destroy해도 해당 리소스는 남도록 관리 범위를 나눴습니다.

비밀값은 코드 밖으로

레지스트리 비밀번호 · API 키는 sensitive 변수로 받고 terraform.tfvars는 git에서 제외, 앱에는 Container Apps secret으로 주입했습니다.

Validation

terraform apply 후 outputs로 앱 URL과 ChromaDB 사설 IP를 확인하고, 앱 ↔ ChromaDB 연동까지 확인했습니다.

AWS로 옮기면

위임 서브넷 → VPC 서브넷 분리 · 사설 IP → Private Subnet + Security Group · Azure Files → EFS · secret → Secrets Manager
